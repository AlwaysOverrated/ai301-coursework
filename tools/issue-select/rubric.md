# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Repo not archived | "archived:" field on the repo line in Repo facts (live mode: the "This repository has been archived" banner on the repo front page) | Fails if archived is yes / banner present | required |
| Repo recently active | "last push to any branch" date in Repo facts, compared against the bundle's capture date (live mode: today) | Passes if the last push was within 180 days of the capture date | required |
| Repo shows human activity | "last 5 default-branch commits" (author names) and "maintainer first-response sample" in Repo facts | Passes if at least one of: (a) any of the last 5 commits was authored/merged by a human within 30 days of the capture date, or (b) at least one sampled issue got a maintainer/owner/collaborator response within 30 days. Fails only if both signals are absent or stale | required |
| Issue has a settled, bounded spec | The issue body, the full comment thread, and the issue's open date vs capture date | Fails if any of: (a) the issue is an explicit tracking/umbrella checklist meant to be split across contributors; (b) the thread shows real disagreement -- more than one person proposing conflicting approaches -- with no maintainer ever settling on one, especially over a long open duration or across abandoned PRs; (c) a maintainer states the fix touches core internals; (d) nobody with authority over the project (a maintainer, collaborator, or owner) has endorsed a direction, AND the request leaves a real product or design decision unmade (whether to build it, what it should look like/do). Passes even when the issue lists multiple named causes or candidate approaches, as long as those come from a single author (e.g. a maintainer's own bug diagnosis) with no unresolved dispute -- offering options is normal scoping, not an unsettled debate. Length and detail do not make an issue unbounded on their own. A short body does not fail by itself if the requested change and its shape are clear and undisputed | required |
| Not a pure support question | The issue body | Fails if the issue is only "how do I get this to work" with no proposed change or bug being reported | required |
| Unclaimed | "this issue: assignees:" and "linked PRs:" fields in Repo facts, plus the comment thread for claim language ("I'll take this", "working on this", "can I work on this") and whether a maintainer acknowledged it | Fails if assignees is non-empty, or if any linked PR is open, or if the thread shows an open, currently-active claim comment. A closed/abandoned linked PR or an old, seemingly-abandoned claim comment does not by itself fail this check. In live mode, per the Path Review house rule in scope.md, other students' claim comments on Path Review issues never fail this check | required |
| AI-contribution policy is not a ban | "contribution policy" line in Repo facts (live mode: CONTRIBUTING.md / AI_POLICY.md / templates, per the evidence guide) | Fails only if the policy states an outright ban on AI-generated code/contributions. Conditions (disclosure, personal understanding, testing, human review) pass, and silence (no policy stated) passes | required |
| Good-first-issue label present | The issue's `labels:` line | Preferred: a `good first issue` (or equivalent) label is a plus, but its absence never fails the issue | preferred |
| Adoption / usage scale | Star count and, where present, "Used by" counter on the repo line | Preferred: higher stars/usage is a mild plus when ranking accepted candidates | preferred |

## Verdict rule

Accept only if every `required` check grades `pass`. A single `required` check graded `fail` rejects the issue. `unclear` on any `required` check is treated as `fail` (an issue you cannot verify is not one you should take). `preferred` checks never affect the verdict; they are used only to rank issues the rubric has already accepted, using the fit profile in `scope.md`.
